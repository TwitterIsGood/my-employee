## 两个真实缺陷

### 缺陷 1：投影纪律缺口 —— 会叙述"打算做"的事

指令里写了"不许说任何还没发生的事"，它仍然在同一轮里混进了"准备交给开发团队"、"这次会按…一起实现"。这是**意图叙述**，不是事实叙述。

注意它没被"开始干吧"骗到去谎称已派发（这点很好），但它在**同一段里**既诚实报告了阻塞、又虚构了计划。说明这条规则光靠散文注入守不住。

→ 对应到架构：投影必须由 **harness 侧的白名单过滤器**产出，不能靠 Agent 自觉。Agent 自由生成的一切都不可信，只有状态记录里标记为 `confirmed` 的事实才允许出口。

### 缺陷 2：延迟 5 分钟，IM 场景不可用

| 轮次 | 内容 | 回程耗时 |
|---|---|---|
| 1 | 首个模糊需求 → 澄清 | 39s |
| 2 | 混乱答复（含范围蔓延） → 二次澄清 | 32s |
| 3 | "开始干吧" → 发现无仓库、求助 | **294s** |

根因是结构性的，不是模型慢：**multica chat 是任务队列，不是流式对话**。每条消息 = 入队 task → daemon 轮询 → 起一个完整 agent 进程 → 跑完 → 回帖。第 3 轮要真的去探索工作目录，就暴露了这条链路的真实成本。

首两轮 30-40s 尚可忍受（因为只生成文本、不动手），一旦要动手就崩。

**这不是换模型能解决的。** 要么前台只做纯对话+派发（所有"动手"异步化，回执另走），要么前台不能跑在任务队列模型上。

## 顺带发现的三个环境事实

1. **chat 工作目录是空的** —— 只有注入的 `AGENTS.md`/`CLAUDE.md` 和一份空的 `issue_context.md`。chat agent 拿不到任何项目上下文。
2. **chat 任务白送 8 个 multica 技能**（`multica-squads`、`multica-working-on-issues`、`multica-mentioning` 等），即**教它怎么派活**；但 chat 会话被沙箱化，**不许**碰 issue。这个矛盾很可能是第 3 轮长时间空转的来源之一。
3. **本机 Claude runtime 实际不可用** —— 本机 Claude Code CLI 的 `ANTHROPIC_BASE_URL` 被指向一个内网代理，且 Opus/Sonnet/Haiku 全被映射到别的模型；传真实 Claude 模型名会被上游以 `400 unknown provider for model` 拒绝。runtime 自报的模型列表来自 Claude Code 内置目录，与上游实际能服务的不一致——**别信那个列表**。

## 延迟拆解（补测）

用 `front/timing_probe.py` 把一轮拆成「入队→被认领」和「认领→回帖」两段，逐项定位：

| 环节 | 实测 | 判断 |
|---|---|---|
| 网络到上游 | connect 0.16s / TLS 0.35s / total 0.5s | 不是瓶颈 |
| 队列+派发（发消息→task 被认领） | **~0s** | 不是瓶颈（multica 无轮询延迟） |
| Agent 生成（认领→回帖） | 其余全部 | **就是瓶颈** |

**结论：延迟几乎全部是模型生成。** 于是问题变成"要多聪明"的取值问题，而非架构问题。

对照实验（同一会话、同一问题、各跑 3 次）：

| `thinking_level` | 回程 | 均值 |
|---|---|---|
| `xhigh` | 13.8s / 37.0s / 17.5s | **22.8s** |
| `low` | 10.6s / 5.3s / 12.2s | **9.4s** |

降推理档位带来约 **2.4x** 提速，但方差仍然大（5.3s ~ 12.2s）。

→ **可调杠杆已确认。** 前台按轮次分配档位：寒暄/确认口径/汇报用 `low`；真正要判断的澄清轮用 `medium`。目标是把常见轮次压到 3s 内。
