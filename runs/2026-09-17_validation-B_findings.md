## 五个 harness 缺陷

### 缺陷 A：05↔06 死锁 —— 契约少了一条边

05 审出真问题，`结论` 照实写 `驳回`、`驳回至` 写 `03`。它**合法地**通过了 05 自己的出口条件（规范里 `结论 ∈ {通过, 驳回}`，`one_of` 落地）——然后被交给 06。06 的入口要 `结论 = 通过`，于是把 05 退回来。05 重新审查、重新得出同一个结论、再次合法通过、再次被退。三次之后撞上限：

```
seq=22 阶段 05 的交付通过出口条件：审查记录
seq=23 type=blocker：对抗式审查的交付被部署验证打回（1 条不通过）
seq=26 type=blocker：…（第 2 次）
seq=29 type=blocker：…（第 3 次）
seq=30 type=blocker：返工 3 次仍未收敛，需要人工指导者介入
```

**这不是两段打架，是契约缺了一条边。** 现有的 `reject_upstream` 管的是**入口**：上游没交够，本段拒绝启动。这里缺的是**裁决**：上游交够了（05 的出口完全达标），但交付物**内容**里写着「退回 03」——出口判定过完之后还有一步没人走。

修法：给阶段加 `reject_on`（契约里机器可读），命中就不 accept，直接把交付物里点名的目标当驳回目标。

→ 对应到架构：**出口条件通过 ≠ 这一趟该往下走。** 判定必须分两层——「交够了吗」（出口条件）和「交的东西说了什么」（裁决路由）。只做前者，任何「审查者说不行」的交付都会被机械地推向下一段。

### 缺陷 B：前台读到的是判定器的机械串，不是审查者的话

修前前台「卡点」那一栏写的是：

> on: 审查记录.结论: 是 驳回，要求 通过（值必须相等）

这是 06 **入口判定器内部**的违规定位串——字段名 + 期望值，是给人调试用的，不是给需求方看的。而审查者真正写下的那段话（一条合法请求就能让整个看板永久 500、重启无效、`/healthz` 仍报 200、门槛只要 ~175 KB）当时根本到不了前台。

根因：`Rejection` 只带了定位信息，没带理由。驳回理由没有跟着驳回一起往回走，**驳回权就成了一道形式**——上游知道「我被退了」，不知道「为什么」。

修后同一栏变成审查者的原话：

> on: 证伪尝试 A 与 B 复现成功，且这是本次变更引入的回归、不是既有风险：变更把 /api/daily 的读路径从「读落盘快照」改成「每次请求全量 ReadAll(logins.jsonl)」…（1）触发门槛比前几轮记的低约 6 倍——请求体只要约 175 KB…（2）该状态下变更卡的回滚方案前置步骤 make reindex 同样失败…

→ 对应到架构：**理由必须和驳回同行。** 判定器负责「哪一条不过」，交付物负责「为什么不过」，前台只许读后者。

### 缺陷 D：断点续跑会丢掉「为什么被退回」（已修）

缺陷 B 把理由接回了驳回，但只接了**一次 Run 之内**：`Runner.back` 是个内存字段，
`remember()` 只写它、不落盘。而链路是会断的——停在等人、撞南墙、某段预算用尽都要断。

于是续跑时那一段**只知道自己叫 03，不知道欠着什么**。它会拿着和上一趟一模一样的输入
再交一遍同样的东西，然后被同一个理由再退回来——驳回权在断点处退化成了一道手续，
和缺陷 B 修之前是同一个病，只是复发的位置换到了进程边界上。

修法：把 `back` 写进 `chain.json`（`State.Back`），Run 开头接着还；这一段交过之后销账。
销账是必需的——留着它，下一趟续跑会拿**两轮以前**的原因去叫醒它，
那比没有原因更坏：它会把一批已经没人要的东西补一遍。

→ 对应到架构：**凡是「跨断点还得成立」的状态，都必须和断点存在同一处。**
判定用到的输入（上游交付物）落在文件里，判定用到的上下文（理由）也得落在文件里。

### 缺陷 E：叫不醒的唤醒没有头，也不出声（已修）

这一趟真正把链路卡住的不是死锁，是这个。

05 按规范自己写探针脚本复现反例，脚本第 8 步开 headless 浏览器 dump DOM，
浏览器卡住不返回，脚本就在前台等着。整条链路停在那儿**二十多分钟**：

- `chain.json` 稳稳写着「停在阶段 05」，看不出异常
- 事件日志最后一条是「进入阶段 05」，前台看到的和「正在跑」一模一样
- 既没往下走，也没走到「撞南墙该升级」的那一刻

比撞南墙更坏：撞南墙会升级给人、会留卡点；叫不醒**两样都没有**。
`dispatch` 里 `r.Worker.Run(ctx, ...)` 连 ctx 都没设时限，`CmdWorker` 用的是
`exec.CommandContext` 却没有 `Cancel`/`WaitDelay`——超时只会 kill 掉 `sh`。

修法（三条一起，缺一条就还是有个洞）：

1. `--wake-timeout`（默认 30m）给一次唤醒设墙钟上限。宽是故意的：
   一次真实的 05 审查实测二十多分钟，这里卡的是「无限」不是「慢」。
2. `Setpgid` + `kill(-pgid)`：唤醒跑的是 `sh -c`，脚本自己会起服务、开浏览器，
   只杀 `sh` 会留下孤儿继续占端口——每超时一次留一个。
3. 叫不醒**要留卡点**（`ErrWakeFailed`，与 `ErrNotConverging` 分开）。
   前台分不清「叫不醒」和「正在跑」，不写事件就没有第二个信号源。
   分开记还避免了让人去改一个本来没问题的交付物。

→ 对应到架构：**「不会一直撞南墙」是个更强的要求，字面上不等于「不会一直卡住」。**
撞南墙是判定层的结论，前提是判定**跑起来了**。判定层下面的那一层（唤醒本身）
如果没跑起来，上面所有的账都不成立。已经写进 [`standards/resilience.md`](../standards/resilience.md) 第 6 条。

### 缺陷 C：白名单里有一半类型没人发（**已修**）

`internal/projection/projection.go:24-27` 的白名单有五个类型：

```
"failure":  {"where", "cause"},
"change":   {"scope"},
"observation": {"metric", "window", "value"},
"blocker":  {"on"},
"decision_needed": {"options"},
```

前台也为它们准备了栏目标题（`:44-45`「已发生的变更」「观测到的数字」）。但把 `internal/` 和 `cmd/` 翻遍，**发事件的只有三处**：`blocker`（pipeline.go:577、dispatch.go:391、chain.go:295）、`decision_needed`（dispatch.go:359）、`progress`。**没有任何代码路径发 `change` / `observation` / `failure`。**

实测分布印证：

```
{'progress': 25, 'decision_needed': 3, 'blocker': 7}     共 35 条
```

后果很具体：这一趟里 03 改了 8 个文件、05 量出了 p99 和「门槛低 6 倍」，前台**一个字都显示不了**——「已发生的变更」和「观测到的数字」这两栏是结构性永远空的。更糟的是 05 在 `待决策` 里留了 4 条只有人才能拍板的问题（KB-A 是修还是带着已知失效上线、单条记录长度上限定多少、时区口径、空白天显不显示 0），其中第一条明写着「这是需求方/人工指导者的决定」——**它一次都到不了前台**，因为 `decision_needed` 只从 dispatch 的 `pause_on` 机制发出来，Agent 写在交付物里的 `待决策` 没有出口。

跑完之后这条更难看了一层。**链路走完全程、返工 1 次、查出一个真 bug 并修好、独立复核过，前台的整份投影是：**

```
# 当前状态

- 阶段：全部阶段已完成
- 上一个已确认的完成点：无

暂无已确认的事实。
```

`lastConfirmed`（`projection.go:258`）读的是最后一条 `change` 事件——没有代码路径发 `change`，所以前台那行**主标题**结构性永远是「无」。不是「话说得不好」，是**没话说**：干了七个阶段，前台只有一句「已完成」加一句「无」。

这是四个缺陷里对前台影响最大的一个：另外三个影响的是「话怎么说」，这个影响的是「有没有话说」。

→ 对应到架构：**投影白名单必须和事件发射端对账。** 白名单是一种承诺——承诺了却没人发，等于前台假装有这两栏。检查方法很土但有效：数一遍 harness 里所有 `"type":` 字面量，和白名单取差集。

反过来说，这一条修好之前，「闸门住在 harness，不住在 Agent 里」这个设计在前台这一侧是**看不出来的**：Agent 交出来的交付物里写满了事实（改了哪些文件、量到了什么、哪四条要人拍板），harness 一个都没往外放。闸门确实在 harness 里，可 harness 也没把该放行的放出来。

#### 修法：加一个 `publish` 字段，事实在被接受的那一刻发出去

投影是**事件日志的纯函数**（`standards/projection.md` 开头那条不变量）——所以事实必须以事件的形式产生，不能改成"投影去读交付物"。那就需要一个地方指定「这份交付物里哪些字段是给前台的」。

阶段契约里新增 `publish`，指向交付物中的一个字段（03~07 统一叫 `前台事实`）：

- **谁发**：harness 在 `accept()` 的那一刻逐条校验、逐条发出。Agent 不必也不许自己举手说「确定」——那正是本档开头「前台会虚构计划」的毛病。
- **顺序**：先写 `accept`、再发事实。反了的话 `resolve()` 会用同一轮里那条 accepted 把刚发的 `decision_needed` 立刻撤掉。
- **缺字段 = 不通过**：声明了 `publish` 却不交那个字段，判为「没交够」并带着原因重跑，最终升级成 blocker。真的没有可报的要写 `[]`。这和 `confirmed` 是同一条纪律：**缺省不等于已确认，缺省等于判不出来。**
- **对账测试**：`TestEveryWhitelistedTypeIsReachable` 把白名单和发射端钉死——白名单里每个类型都必须指得出谁发它，两边任一多出一个就失败。这条是前面那个「数一遍字面量」的人工检查的机器形态。

#### 验收时又揪出两个

按验收标准拿这趟的真实产物重投，前台确实显示了「9 个文件」「门槛低 6 倍」和待决策——但顺路暴露了两个**从没被走过所以从没被发现**的错：

1. **`options` 的类型对不上。** `publishOptions` 返回 `[]string`，而投影器数选项条数用的是 `ev["options"].([]any)`——断不过去，一条选项齐备的 `decision_needed` 到那儿被判成"0 个选项"，**整次投影直接报错**。这个错在落盘那条路上看不见：JSON 一来一回会把 `[]string` 重新解成 `[]any`，所以端到端测试照样绿，只有不经磁盘、直接拿内存里那张 map 去投影的路径会中招。修法是发 `[]any`，和 `pause_on` 那条同形。
2. **字段名是英文的。** `render` 直接印事件里的键，前台看到的是 `metric: …` `window: …` `scope: …`。这两类事件在修好之前一条都没有，所以那行代码从没被执行过。修法是加一张 `labels` 表（指标/窗口/数值/影响面/位置/原因/卡在）。

两个都用**不落盘**的方式各钉了一条测试——落盘会把这类形状错误洗干净，那正是它们能藏这么久的原因。

## 靶子上的真实缺陷（KB-A）

**一条完全合法的 `POST /login` 就能永久打坏整个看板。**

```
基线 GET /api/daily                      → 200
POST /login（user_id 长 2000000）        → 200 {"ok":true}
GET /api/daily                           → 500  bufio.Scanner: token too long
GET /api/daily?day=2026-09-07（历史天）  → 500
重启服务                                  → 仍 500
GET /healthz                             → 200   ← 存活探针发现不了
对照：同一份数据、改动前的旧二进制         → 200   ← 回归由此坐实
```

阈值实测：`len=1048500 → 200`，`len=1048577 → 500`（`internal/logstore/store.go:63` 的 1 MiB scanner 上限）。

机理：`store.go:70-72` 遇到**任何一行**读不了就整体 `return nil, err`；`api.go:133-137` 每次请求 `ReadAll()` 并把它直接变成 500；写入端 `api.go:73` 只校验 `user_id != ""`，不限长度。改动前读的是落盘快照、压根不碰 `logins.jsonl`，所以这是本次变更引入的。

两条是这一趟新查出来的：

1. **门槛比先前记的低约 6 倍。** `encoding/json` 默认开 HTML 转义，一个 `&` 会被写成 6 字节的转义序列（`u0026` 前面加一个反斜杠），所以请求体只要 **~175 KB**（175000 个 `&`）就能落出一条 1050049 字节的行。原来记的「要 1 MB 量级、不常见」这个安慰性判断不成立。
2. **回滚路径在最需要它的时候不可用。** `-reindex` 也报同样的 `token too long`、exit 1（`ReadAll` 先报错，`main.go:32-44` 直接 return），而变更卡把「回滚前必须先 reindex」写成了前置条件。

**三方对同一件事的处置方式，是这一趟最像样的部分：**

- **03** 复现了 KB-A，写进变更卡，**但不修**——理由是「修它必然改动 diff，04/05 的全部证据都建立在现 diff 上，改完两者一并失效」。
- **04** 独立复现（不是转述 05），把 3 条断言失败连同完整输出和退出码落盘，**不打回 03**——因为规范列的三条驳回条件逐条核对均不成立。
- **05** 连续四次拒绝把 `结论` 改成 `通过`，并在记录里新增一栏「下游要求与本记录结论的冲突」，把 06 的打回次数和「这不属于规范条款」写清楚。它给 03 的建议是两条一起做：(a) 写入端给 `user_id` 设长度上限并与读端对齐；(b) 读路径区分「文件读不了」与「某一行坏」，明确坏行的降级语义。只做 (a) 挡不住已经落盘的坏行。

→ 这三段合起来说明一件事：**「发现自己修不动」和「宣布自己没问题了」是两回事，而 Agent 有能力区分。** 需要 harness 提供的不是判据，是**把决定权退回去的路**——04 退给 05/06，05 退给 02（「若 03 判定降级策略超出实现范围，按规范该升级到 02，而不是改结论」）。这条退的路现在是明的，但**退出去的信号到不了前台**（缺陷 C）。
