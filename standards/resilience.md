# 上游韧性（从一次真实故障里总结）

2026-09-16 实测故障：`<内网代理>` 的 codex 池返回
`503 auth_unavailable (providers=codex, model=gpt-5.6-sol; server_is_overloaded)`。
前台 Agent 的表现是：**烧掉 38～202 秒，然后把 503 原文丢给需求方看。**

这就是"一直撞南墙"的一个真实样本。总结成四条硬要求。

## 1. 「两个 runtime」不等于「两个 provider」

本机三个 multica runtime（codex / claude / antigravity）最终都汇到**同一个代理的同一个池子**。上游一挂，换 runtime 救不了——实测 `gpt-5.6-sol` 和 `gpt-5.5(xhigh)` 同时 503。

**要求**：冗余要按**上游出口**算，不是按 runtime 个数算。选型时必须回答："这两个入口，最坏情况下会不会同时挂？" 会，就不算冗余。

## 2. 失败必须有界

实测一次失败烧了 **202 秒**（内部无限重试到超时）。IM 场景下这比直接报错还糟——需求方盯着一个转了三分钟的圈。

**要求**：单次上游调用必须有**硬超时**；超时后立刻**降级到下一个出口**，而不是原地重试。总时长上限应是"人类还愿意等"的量级（前台 ≤ 10s）。

## 3. 上游错误不许透传给需求方

前台把 `503 auth_unavailable: no auth available (providers=codex...)` 原样送进了聊天窗口。

**要求**：上游故障属于**后台过程**，走 [`projection.md`](projection.md) 的黑名单。需求方最多看到"暂时联系不上，正在换通道重试"；具体 provider / model / status code 是运维信息，不是交付信息。

更好的做法是**根本不让它出现**——降级成功的话，需求方不该知道主通道挂过。

## 4. 降级路径必须被测量过，不能只是写着

"有备胎"和"备胎能用"是两回事。

**要求**：每个降级出口都要有**实测记录**（什么时候测的、走的什么请求、延迟多少）。没测过的备胎等于没有。
