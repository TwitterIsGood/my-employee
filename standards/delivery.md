# 交付标准（单一事实源）

这份文件是**唯一**的事实源。它被渲染成两种形态：

- **形态 A（散文注入）** —— 每轮注入 Agent 的系统提示，让 Agent 知道规则。
- **形态 B（闸门谓词）** —— 注入 harness 的 hook 判定，让规则**无法被跳过**。

改规则只改这里。两形态由脚本从本文件生成，禁止手改生成物。
每个 `[闸门]` 块必须有一条机器可判定的谓词；写不出谓词的准则视为**未落地**。

---

## 一、六要两不要（顶层研发规范）

### 1. 要测试

> 变更前要测试，测试场景要完备（从场景、接口、代码等维度作出覆盖；复杂变更应在测试环境验证变更方案和回滚方案）。

- `[闸门]` 提交变更前，**回归套件全绿**（exit 0）。变更涉及的包，其测试文件必须存在且被本次变更触及或覆盖。
- `[闸门]` 若变更触及线上数据路径（迁移/回填/删除），必须在**测试环境**跑通方案与回滚方案，产出可复现的命令日志。仅有本机通过不算。
- `[证据]` 测试命令 + 退出码 + 失败用例输出；测试环境执行的完整命令与日志路径。
- `[反例]` "我人工检查过了" / "测试已在之前跑过" / 无退出码的测试摘要。

### 2. 要周知

> 变更前要周知，周知范围要全面（高危操作必须经过受影响方的人工确认）。周知对象：内部团队、运维团队、业务使用方等。

- `[闸门]` 变更卡必须显式列出**受影响方**及其确认状态；高危操作（不可逆 / 影响线上数据 / 影响可用性）的受影响方确认必须是 **`confirmed`**，不能是 `assumed`。
- `[证据]` 变更卡里的受影响方清单 + 每个的确认状态与确认来源。
- `[反例]` 受影响方为空；状态是"应该没人受影响"。

### 3. 要审核

> 变更前发起审核，重点审核测试报告、变更时间、变更步骤、变更风险、观测指标、回滚方案。

- `[闸门]` 变更卡六个字段**必须全部非空**：`测试报告` / `变更时间` / `变更步骤` / `变更风险` / `观测指标` / `回滚方案`。缺一即驳回。
- `[闸门]` `回滚方案` 必须是**可执行命令或步骤**，不是"回滚代码"这种描述。
- `[证据]` 变更卡本身（JSON），六个字段的原文。

### 4. 要灰度

> 变更过程要灰度，灰度影响范围要可控（单机到单机房逐步灰度，或从单业务线到多业务线）。

- `[闸门]` `变更步骤` 必须包含**至少两级**影响面递进（例如 单机 → 全部），且每级之间有观测点。
- `[闸门]` **不存在**一步到全部影响面的变更步骤序列（除非该变更是纯文档/无运行时影响，需显式声明 `blast: none` 并给出理由）。
- `[证据]` 变更步骤原文 + 每级的观测窗口与结论。

### 5. 要观测

> 变更结果要可观测，变更期间及时查看监控和日志（观测一定时间后确保无异常方可进行后续动作）。

- `[闸门]` 每一级灰度后必须有一段**已完成的**观测记录，含：观测指标名、时间窗口、实际读数、结论。观测窗口**未走完**不得推进下一级。
- `[证据]` 指标时间序列或查询命令 + 输出 + 时间戳。
- `[反例]` "没看到报错" / 无时间窗口的"正常"。

### 6. 要可回滚

> 变更要有回滚方案且可快速执行（包含代码回滚和数据回滚；变更前制定好回滚预案）。

- `[闸门]` `回滚方案` 必须**同时覆盖**代码回滚与数据回滚（若本次变更不涉及数据，显式声明 `data_rollback: n/a` + 理由）。
- `[闸门]` 回滚方案必须在**测试环境预演过至少一次**，产出命令日志。
- `[证据]` 回滚预演的命令与日志。

### 7. 不要瞒报故障

> 变更导致线上问题后，及时周知相关方。

- `[闸门]` 一旦观测到异常，`故障上报` 必须置位，且**在继续任何操作之前**完成；上报对象与准则 2 的受影响方清单一致。
- `[闸门]` 故障期间禁止继续推进灰度或执行回滚以外的变更步骤。
- `[证据]` 异常发现时间戳 → 上报时间戳 → 上报对象记录。

### 8. 不要违规变更线上数据

> 禁止通过 Staging 环境去变更线上数据；建议不要留后门。

- `[闸门]` 任何指向线上数据源的连接串 / 凭证，**不得**出现在 staging 环境的配置、环境变量或执行日志中。静态扫描 + 运行期环境检查。
- `[闸门]` 代码变更中不得新增绕过鉴权/审计的分支（新增的 `if debug` / `skip_auth` / 硬编码凭证 / 直连生产库的脚本）。
- `[证据]` 扫描命令与输出；相关 diff。

## 二、闸门的执行位置

闸门住在 **harness**，不住在 Agent 里。理由：harness 是唯一同时接触「模型说了什么」和「环境真的发生了什么」的一层，只有它能判定。

- **形态 B** 由 Trellis 的 hook 层承载（`UserPromptSubmit` 注入状态、`PreToolUse` 拦截），因为 worker 本身就跑在 Claude Code / Codex CLI 里，闸门跟着 worker 走，与谁派活的无关。
- 六要两不要是**唯一**一组规则，两形态从同一份文件生成，由 `render.test` 保证：每个 `[闸门]` 谓词在形态 A 里都有对应的散文句子，反之亦然。任一方向缺失即测试失败。

`[闸门]` 参照 Trellis 的 `regression.test.ts` 惯例：**每一个 `[required · once]` 步骤，必须有一条对应的强制行**，否则 AI 会静默跳过它。

## 三、每条准则在哪一段被强制执行

这份文件是**全局**准则，但它不在每个阶段平均发力。哪条准则归哪个阶段管，
见 [`stages/index.md`](stages/index.md) 的映射表——那是全局层与阶段层之间**唯一**的连接点。

阶段文件不复制本文件的条文，只说"这一段要守第几条"。
于是改一条准则只需要改一处，而各阶段的专属规则又各自成文。
