# 投影规则（前台能看到的 vs 看不到的）

**问题**：验证 A 测出前台 Agent 会在同一段话里既诚实报告阻塞、又虚构计划（"准备交给开发团队"、"这次会按…实现"）。指令里写死了"不许说没发生的事"，它还是说了。

**结论**：投影**不能**靠 Agent 自觉。必须由 harness 侧的非 Agent 进程产出，前台只读它的输出。

## 机制

```
后台事件日志（raw，前台永远拿不到路径）
        │
        ▼   project.py —— 非 Agent，纯函数，无模型
        │
        ▼
projection.md（前台唯一能看到的东西）
```

前台 Agent 的工作目录里**只有** `projection.md`。原始日志在另一个目录，前台既没有路径也没有理由去找。

## 白名单：只有这些类型能出口

| `type` | 含义 | 必备字段 |
|---|---|---|
| `failure` | 已确认的失败 | `where`（确切位置）、`cause`（原因） |
| `change` | 已实际发生的变更 | `scope`（影响面） |
| `observation` | 观测到的真实数字 | `metric`、`window`、`value` |
| `blocker` | 阻塞点 | `on`（卡在什么上） |
| `decision_needed` | 需要需求方拍板 | **`options`（选项数组，至少 2 个）** |

## 黑名单：一律不出

`retry` · `hypothesis` · `debate` · `progress` · `intent` · `plan` · `draft`

判定标准是**确定性，不是好坏**：
- "前两种思路验证行不通，原因都是 X" → ✅ `failure`，已确认
- "现在在试第四种，应该快好了" → ❌ `intent` + `hypothesis`，没发生
- "开发和审查对加不加缓存有分歧" → ❌ `debate`；但如果有明确的二选一 → ✅ `decision_needed` 带 `options`
- "一切正常，进展顺利" → ❌ `progress`，零信息量

## 三条硬校验

1. **`decision_needed` 必须带 `options`。** 不带选项的"需要你决定"等于把后台的纠结原样倒给需求方。
2. **每条出口记录必须有 `evidence`。** 没有可复现证据的"事实"只是另一种猜测。
3. **白名单类型必须显式标 `"confirmed": true`。** **类型对不代表事实对**——
   一条 `type=change` 完全可以写成"我们准备把活跃度改成只统计 last_login_at"。
   标注规则：

   | `confirmed` | 处理 |
   |---|---|
   | `true` | 出口 |
   | `false` | 不出，**不算错**（这件事本来还在飞，后台就该记在途事项） |
   | 缺省 | **报错退出**——判不出来。**缺省不等于已确认**，这条是它的全部意义 |

`project.py` 对违反这三条的记录**直接报错退出**，不静默丢弃——静默丢弃会让后台以为自己上报了。
只有两种"不出"是正常的：黑名单类型、和显式标了 `confirmed=false` 的在途事项。

校验逻辑的可执行版本在 [`back/test_projection.py`](../back/test_projection.py)，
含构造的验收用例：「我们准备…」（类型合法但未确认）必须被拦下。
