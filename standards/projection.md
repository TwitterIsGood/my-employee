# 投影规则（前台能看到的 vs 看不到的）

**问题**：验证 A 测出前台 Agent 会在同一段话里既诚实报告阻塞、又虚构计划（"准备交给开发团队"、"这次会按…实现"）。指令里写死了"不许说没发生的事"，它还是说了。

**结论**：投影**不能**靠 Agent 自觉。必须由 harness 侧的非 Agent 进程产出，前台只读它的输出。

## 机制

```
后台事件日志（raw，前台永远拿不到路径）
        │
        ▼   project.py —— 非 Agent，纯函数，无模型
        │
        ▼
projection.md（前台唯一能看到的东西）
```

前台 Agent 的工作目录里**只有** `projection.md`。原始日志在另一个目录，前台既没有路径也没有理由去找。

## 白名单：只有这些类型能出口

| `type` | 含义 | 必备字段 |
|---|---|---|
| `failure` | 已确认的失败 | `where`（确切位置）、`cause`（原因） |
| `change` | 已实际发生的变更 | `scope`（影响面） |
| `observation` | 观测到的真实数字 | `metric`、`window`、`value` |
| `blocker` | 阻塞点 | `on`（卡在什么上） |
| `decision_needed` | 需要需求方拍板 | **`options`（选项数组，至少 2 个）** |

## 谁把事件放进日志

白名单是**承诺**，得有谁去兑现。承诺了没人发，前台就在假装有那一栏——
而且编译得过、跑得通、测试全绿，只是没人发现。

| 类型 | 谁发 |
|---|---|
| `blocker` | `internal/dispatch`（出口判定不过 / 入口被打回）与 `internal/chain`（撞返工上限） |
| `decision_needed` | `internal/dispatch`：`pause_on`（停下来等人）、以及交付物里 `publish` 的待决策项 |
| `change` / `observation` / `failure` | 交付物里的 `publish` 字段：本段**被接受的那一刻**，由 harness 逐条校验后发出 |

「被接受的那一刻」是有意的：一份交付通过了出口条件，它声明的事实才算已确认。
Agent 不必、也不许自己举手说「确定」——那正是本档开头那个「前台会虚构计划」的毛病。
形状与校验规则见 [`stages/index.md`](stages/index.md#契约块规则只有一个事实源)。

**这条边曾经整个是断的**：一趟七段链路跑完，投影里有「已发生的变更」「观测到的数字」
两个标题，而 03 改的 9 个文件、05 量出的「门槛低 6 倍」一条都进不来——harness 里
没有任何代码路径发这三类，前台的整份投影只有「全部阶段已完成」加一句
「上一个已确认的完成点：无」。所以白名单和发射端之间现在有一道对账测试
（`internal/dispatch`）：白名单里每个类型都得能指得出谁发它。

## 黑名单：一律不出

`retry` · `hypothesis` · `debate` · `progress` · `intent` · `plan` · `draft`

判定标准是**确定性，不是好坏**：
- "前两种思路验证行不通，原因都是 X" → ✅ `failure`，已确认
- "现在在试第四种，应该快好了" → ❌ `intent` + `hypothesis`，没发生
- "开发和审查对加不加缓存有分歧" → ❌ `debate`；但如果有明确的二选一 → ✅ `decision_needed` 带 `options`
- "一切正常，进展顺利" → ❌ `progress`，零信息量

## 「卡点」和「需要你决定」有生命周期

这两类记的是**某一段当时的处境**，不是发生过的事——所以它们会被撤下来。

| 事件 | 处境结束的信号 | 撤不撤 |
|---|---|---|
| `blocker` | 它 `stage` 指的那一段后来被接受了 | 撤 |
| `decision_needed` | 同上 | 撤 |
| `failure` / `change` / `observation` | —— | **永不撤**，它们记的是发生过的事 |

「这一段被接受了」是一条 `outcome: "accepted"` 的事件，由派活的一层在出口判定通过时写。
撤回的判据是**更晚**：先通过、再被打回，卡点是新的那个，不许被旧账抹掉。

**不撤会出什么事，是真实跑出来的**：一条需求走完 01→07，投影里写着
「阶段：全部阶段已完成」，墙上却还挂着几小时前那条「本地开发 的交付被 部署验证 打回」。
需求方读到的是「做完了」加「卡住了」——比不报还坏，因为他不知道该不该管它。

同一件事问两遍同理：01 停下来问过一次口径，答复回来、01 接着往下走了，
那条「需要你决定」就必须消失，否则需求方要回答同一个问题第二次。

## 三条硬校验

1. **`decision_needed` 必须带 `options`。** 不带选项的"需要你决定"等于把后台的纠结原样倒给需求方。
2. **每条出口记录必须有 `evidence`。** 没有可复现证据的"事实"只是另一种猜测。
3. **白名单类型必须显式标 `"confirmed": true`。** **类型对不代表事实对**——
   一条 `type=change` 完全可以写成"我们准备把活跃度改成只统计 last_login_at"。
   标注规则：

   | `confirmed` | 处理 |
   |---|---|
   | `true` | 出口 |
   | `false` | 不出，**不算错**（这件事本来还在飞，后台就该记在途事项） |
   | 缺省 | **报错退出**——判不出来。**缺省不等于已确认**，这条是它的全部意义 |

`project.py` 对违反这三条的记录**直接报错退出**，不静默丢弃——静默丢弃会让后台以为自己上报了。
只有两种"不出"是正常的：黑名单类型、和显式标了 `confirmed=false` 的在途事项。

校验逻辑的可执行版本在 [`internal/projection/projection_test.go`](../internal/projection/projection_test.go)，
含构造的验收用例：「我们准备…」（类型合法但未确认）必须被拦下。

## 闸门怎么接进来

规则写在文档里会腐，所以真正生效的是 harness 侧的一个进程，
Agent 每轮的上下文由它产生、且**只由它产生**：

```
后台事件日志（raw，前台永远拿不到路径）
        │
        ▼   cmd/gate —— UserPromptSubmit hook，非 Agent
        │     投影器报错时 fail-closed 到「状态不可读」，不是放行
        ▼
projection.md（前台唯一看得到的东西）+ 注入当轮上下文
```

Agent 跑起来时通过 `--settings` 带上这个 hook，见 [`resilience.md`](resilience.md) 第 5 条。
