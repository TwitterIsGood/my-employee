# 阶段 05：对抗式审查

> 试图证伪，不是复读测试报告。

## 职责

**只**找问题。目标不是确认变更对，而是**尽力证明它错**。找不到反例本身就是结论，但那必须是尝试过之后才有的结论。

**不**写代码（发现问题打回 03）。**不**复述"测试都过了"。

## 入口条件

上游（03 变更 + 04 测试报告）须交付：

- diff
- 测试报告（含退出码与**未覆盖场景清单**）

拿不到就打回 04。**没有未覆盖清单就没法审**——那等于让审查者把已经覆盖的东西再测一遍，没覆盖的一块没碰。

## 出口条件

下游（06 部署验证）接受这份交付，当且仅当：

- 审查结论明确为 `通过` 或 `驳回`（没有"基本可以"）
- 至少一条**尝试证伪**的动作及其结果（怎么试的、结果如何）
- 驳回 → 附可复现的反例
- 通过 → 显式列出**仍未覆盖**的范围（那是 06 的风险输入）

## 专属规范

- **角色隔离**：审查者不得是本案的开发者。同一个 Agent 既写又审，等于没有审查。
- 审查重点在 04 的「未覆盖场景」和边界条件上——已覆盖的部分再测一遍是浪费。
- 只提**能复现**的问题。提不出复现路径的担忧，标成风险，不要伪装成缺陷。
- 通过也不代表没风险。列出未覆盖范围，让 06 带着已知风险上灰度。

## 闸门

- `[闸门]` 审查记录含 ≥1 条证伪尝试及其结果。
- `[闸门]` `结论 ∈ {通过, 驳回}`；`通过` 必须同时给出非空 `未覆盖范围`。
- `[闸门]` `驳回` 必须附可复现反例（命令/输入 + 实际输出）。
- `[闸门]` 审查者身份 ≠ 本案开发者（角色隔离，机器可判定）。

## 驳回权

| 什么情况 | 打回给谁 | 附什么 |
|---|---|---|
| 04 的测试报告缺退出码或缺未覆盖清单 | 04 | 缺哪项 |
| 发现变更本身有问题 | 03 | 可复现反例 |
| 发现方案存在结构性缺陷（不是实现 bug） | 02 | 缺陷说明 + 影响面 |
| 发现需求定义本身有歧义（改不了的情况） | 01 | 歧义点，请需求方确认 |

最后一栏要慎用：**回到 01 意味着范围可能变**，那是需求方的决定，不是流水线的决定。

## 证据

审查记录：证伪尝试清单、结论、反例（若有）、未覆盖范围。

## 反例

- ❌ "测试都过了，代码看起来没问题。" → 复读，不是审查。没有证伪尝试。
- ❌ 开发自己审自己。→ 角色不隔离。
- ❌ 结论写"基本可以上线，小问题后续优化"。→ 没有 `通过/驳回` 二值，06 无法据此决策。
- ❌ 提了一堆"可能有问题的地方"但没有一条能复现。→ 那是噪声，不是审查产出。

## 契约（机器可读）

`结论 ∈ {通过, 驳回}` 用 `one_of` 落地——"基本可以上线"是写不进去的，它不是一个合法的值。

```json
{
  "id": "05",
  "name": "对抗式审查",
  "produces": "审查记录",
  "entry": [
    { "from": "测试报告", "field": "退出码", "check": "present" },
    { "from": "测试报告", "field": "未覆盖场景", "check": "present" }
  ],
  "exit": [
    { "field": "结论", "check": "one_of", "value": ["通过", "驳回"] },
    { "field": "证伪尝试", "check": "min_items", "value": 1 },
    {
      "when": [{ "field": "结论", "check": "equals", "value": "通过" }],
      "field": "未覆盖范围",
      "check": "nonempty"
    },
    {
      "when": [{ "field": "结论", "check": "equals", "value": "驳回" }],
      "field": "反例",
      "check": "nonempty"
    }
  ],
  "reject_to": "04"
}
```
