# 阶段 06：部署验证

> 变更卡齐全、灰度有观测、异常先上报。

## 职责

**只**执行已审核过的变更，并按六要两不要把每一步留痕。

**不**在变更过程中做方案调整（那不是"顺手"，是未经审核的改动）。观测到异常先执行准则 7，动了就来不及了。

## 入口条件

上游（05 对抗式审查）须交付：

- `通过` 结论 + 未覆盖范围清单
- 完整变更卡（六字段）

拿不到就打回 05。**变更卡缺字段就上线，等于准则 3 被跳过**——这一条驳回没有任何商量余地。

## 出口条件

下游（07 回归）接受这份交付，当且仅当：

- 变更卡六字段齐全：`测试报告` / `变更时间` / `变更步骤` / `变更风险` / `观测指标` / `回滚方案`
- **每个灰度级别**都有已完成的观测记录（指标名、时间窗口、实际读数、结论）
- 回滚方案在**测试环境预演过**，有命令日志
- 若观测到异常：`故障上报` 已置位，且上报时间戳早于任何后续操作

## 专属规范

本阶段是六要两不要的主要执行地：准则 **2 周知 / 3 审核 / 4 灰度 / 5 观测 / 6 可回滚 / 7 不瞒报故障**。

- 高危操作（不可逆 / 影响线上数据 / 影响可用性）的受影响方确认必须是 `confirmed`，不能是 `assumed`。
- 灰度至少两级影响面递进，每级之间有观测点。
- 观测窗口**未走完**不得推进下一级。"没看到报错"不是观测记录。

## 报给前台（`前台事实`）

形状和四条规矩见 [index.md](index.md#契约块规则只有一个事实源)。这一段通常报：

| 报什么 | 类型 | 取自 |
|---|---|---|
| 上线这件事本身、影响面到了哪一级 | `change` | `灰度级别` / `最终状态` |
| 观测窗口里的样本数与异常率 | `observation` | `观测记录` |
| 灰度中确认的异常 | `failure` | `观测到异常` + `故障上报详情` |
| 带着上线的已知风险要不要处理 | `decision_needed` | `待决策` / `未闭合项与处置` |

准则 7（不瞒报故障）在这一段靠 `故障上报` 字段落地，**报给前台靠 `failure`**——
只把 `故障上报` 置成 `true`，需求方读到的是一句「报过了」，读不到报的是什么。

## 闸门

- `[闸门]` 变更卡六字段全部非空，缺一即驳回。
- `[闸门]` `回滚方案` 是可执行命令或步骤，不是"回滚代码"这类描述。
- `[闸门]` `变更步骤` 含 ≥2 级影响面递进，且**不存在**一步到全部的序列（纯文档变更需显式声明 `blast: none` 并给理由）。
- `[闸门]` 每级灰度后有已完成的观测记录；观测窗口未走完不得推进。
- `[闸门]` `回滚方案` 同时覆盖代码回滚与数据回滚（不涉及数据须显式 `data_rollback: n/a` + 理由）。
- `[闸门]` 异常一旦观测到，`故障上报` 置位时间戳**早于**之后的任何变更步骤时间戳。

## 驳回权

| 什么情况 | 打回给谁 | 附什么 |
|---|---|---|
| 变更卡缺字段 / `回滚方案` 不是可执行步骤 | 03 补，05 复审 | 缺的具体字段 |
| 受影响方确认是 `assumed` | 01 | 需需求方确认的周知范围 |
| 05 未列出未覆盖范围 | 05 | 补清单 |
| 观测窗口未走完就被推进了下一级 | 拒绝推进 | 要求补齐观测记录 |

第三行回到 01 是个**有意的设计**：周知范围由影响面决定，而影响面改不改是需求方的判断。

## 证据

变更卡（JSON）+ 每级灰度的观测记录（指标、时间窗口、读数、结论）+ 回滚预演日志 + 故障上报时间戳链。

## 反例

- ❌ 变更步骤只有"全量发布"一步。→ 违反准则 4。
- ❌ "没看到报错，继续下一步。" → 无时间窗口、无指标名、无读数，不是观测。
- ❌ 回滚方案写"回滚代码到上一版本"。→ 不是可执行步骤，准则 3 明确要求。
- ❌ 观测到异常后先回滚、再周知。→ 顺序反了，准则 7 要求上报在继续任何操作**之前**。
- ❌ 通过 Staging 环境的连接串去改线上数据。→ 准则 8。

## 契约（机器可读）

六字段写死在 `entry` 里——变更卡缺一个字段，06 连开工的资格都没有，这是准则 3 的机器形态。
`故障上报` 那条带前置：没观测到异常时不要求它，观测到了就必须置位。

```json
{
  "id": "06",
  "name": "部署验证",
  "produces": "上线记录",
  "entry": [
    { "from": "审查记录", "field": "结论", "check": "equals", "value": "通过" },
    { "from": "审查记录", "field": "未覆盖范围", "check": "present" },
    { "from": "变更卡", "field": "测试报告", "check": "nonempty" },
    { "from": "变更卡", "field": "变更时间", "check": "nonempty" },
    { "from": "变更卡", "field": "变更步骤", "check": "min_items", "value": 2 },
    { "from": "变更卡", "field": "变更风险", "check": "nonempty" },
    { "from": "变更卡", "field": "观测指标", "check": "nonempty" },
    { "from": "变更卡", "field": "回滚方案", "check": "nonempty" }
  ],
  "exit": [
    { "field": "观测记录", "check": "min_items", "value": 2 },
    { "field": "回滚预演日志", "check": "nonempty" },
    {
      "when": [{ "field": "观测到异常", "check": "is_true" }],
      "field": "故障上报",
      "check": "is_true"
    }
  ],
  "publish": "前台事实",
  "reject_to": "05",
  "reject_upstream": { "变更卡": "03" }
}
```

`变更步骤` 用 `min_items: 2` 落地准则 4 的「至少两级影响面递进」——一步到全量的序列在结构上就过不了。

`reject_upstream` 落地上面驳回权表的第一行：**变更卡缺字段是 03 的活，不是 05 的活**。
少了这一句，机器会把"变更卡缺字段"也打回 05，而 05 手里根本没有那张卡——上游会收不到该补的东西。

六字段里 `测试报告` 指向 04 的产物，03 在自己那一步交不出来（见 [03-develop.md](03-develop.md) 的契约一节）。
所以**真实链路每一趟都至少把 03 退回来一次**，让 03 照这里点名的条补交，04、05 跟着重判，然后再进来。
打回时那几条具体缺什么，必须进 03 下一次的 prompt——`cmd/chain` 的 `Reasons` 干的就是这件事。
少了它，03 会拿着一样的输入再交一遍同样的东西，一路撞到返工上限。
