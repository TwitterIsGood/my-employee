# 阶段 02：技术方案设计

> 给出可执行的方案和它的取舍。不写代码。

## 职责

**只**出方案：怎么做、影响谁、代价是什么、拿不准的是哪些。

**不**改代码、**不**跑迁移、**不**自作主张定产品口径。方案里凡是没有证据支撑的推断，都必须标成假设——这是本阶段最容易失守的地方。

## 入口条件

上游（01 需求澄清）须交付：

- 需求定义卡，且 `确认状态 = confirmed`。

拿不到就打回 01。**尤其当 `范围外` 是空的**——边界不明就设计，等于替需求方做了一个他没同意的决定。

## 出口条件

下游（03 本地开发）接受这份交付，当且仅当方案卡满足：

- `做法`：具体到能被实施，不是方向性描述
- `影响面`：非空（改哪些文件/服务/表/接口，谁在依赖它）
- `风险`：至少一条已识别的风险
- `验证方式`：怎么算做成了
- 凡未经验证的推断，字段标 `hypothesis`（**不得**进入前台投影，见 [`projection.md`](../projection.md)）
- 若存在多个合理解法且取舍不同 → 产出 `decision_needed`，带 ≥2 个选项，交需求方拍板

## 专属规范

- **有多个合理解法时，把取舍摆给需求方，不要自己选。** 技术怎么做是你的事，值不值得是需求方的事。
- **技术可行性存疑时找人工指导者**，不要拿去问需求方——那是在浪费他时间（见双平面升级表）。
- 假设必须显式标注。写进方案的"应该"、"大概"、"可能"，等于把猜测伪装成事实传下去。

## 闸门

- `[闸门]` 方案卡含非空 `影响面` 与至少一条 `风险`。
- `[闸门]` 方案里每条推断都带 `hypothesis: true` 或 `confirmed: true` 标记；未标记的推断视为**未落地**。
- `[闸门]` 若方案卡标了 `hypothesis`，它**不得**出现在前台投影里（投影层已强制，见 `projection.md` 第三条硬校验）。
- `[闸门]` 涉及改变现有行为时，`影响面` 必须回答"谁在依赖它"；答不出即驳回。

## 驳回权

| 什么情况 | 打回给谁 | 附什么 |
|---|---|---|
| 需求定义的 `范围外` 为空，或 `确认状态 ≠ confirmed` | 01 | 缺的具体字段 |
| 方案需要需求方在不知道取舍的情况下拍板 | 补 `decision_needed` | 两个选项各自的代价 |

## 证据

方案卡（JSON）+ 支撑它的查询/实测输出（例如"这个字段有没有索引"要贴 EXPLAIN，不是"应该没有"）。

## 反例

- ❌ **真实事故**："活跃度可能可以直接从已有的 audit_log 推出来"（`hypothesis`）被当成方案推进，两轮之后才发现 `audit_log` 没有 `(user_id, created_at)` 复合索引，单用户 7 天窗口退化成顺序扫描、42.7 秒超时。→ 一条没标注的假设，烧掉了整个 03 阶段。
- ❌ "开发和审查对要不要加缓存有分歧，他们在讨论。" → 后台争论属于投影黑名单（`debate`）；有明确二选一就产出 `decision_needed` 带选项。

## 契约（机器可读）

`未标注推断` 要求为 `empty`：方案卡必须显式回答"还有没有没标注的推断"，答案是"没有"才放行。
把它写成 `[]` 是允许的，缺了这个字段不是——**说不清 = 未落地**。

```json
{
  "id": "02",
  "name": "技术方案设计",
  "produces": "方案卡",
  "entry": [
    { "from": "需求定义卡", "field": "范围外", "check": "nonempty" },
    { "from": "需求定义卡", "field": "确认状态", "check": "equals", "value": "confirmed" }
  ],
  "exit": [
    { "field": "做法", "check": "nonempty" },
    { "field": "影响面", "check": "nonempty" },
    { "field": "风险", "check": "min_items", "value": 1 },
    { "field": "验证方式", "check": "nonempty" },
    { "field": "未标注推断", "check": "empty" }
  ],
  "reject_to": "01"
}
```
