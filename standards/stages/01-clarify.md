# 阶段 01：需求澄清

> 把需求方嘴里模糊的话变成可执行的需求定义。

## 职责

**只**澄清。把"我想要个活跃度看板"变成目标、边界、验收标准都明确的一件事。

**不**做技术方案、**不**估工期、**不**写代码。澄清阶段一旦开始谈实现，需求方就被拖进了他不需要做的技术判断里。

## 入口条件

需求方给了一段话（可能很粗）。这是**唯一**没有上游产物的阶段——它的上游是人。

## 出口条件

下游（02 方案设计）接受这份交付，当且仅当需求定义卡满足：

- `目标`：一句话，不含实现细节
- `范围内`：非空
- `范围外`：**非空**（空 = 没想过边界，这是最常见的问题）
- `验收标准`：可判定（"好用"不行，"响应 < 500ms"可以）
- `确认状态 = confirmed`——需求方本人确认过，不是 `assumed`

## 专属规范

- 范围、优先级、取舍、要不要做——**这些是需求方的权力，不是你的**。你绝不能自己发明会改变范围的产品决定。
- 能自己查代码/文档得出结论的，不要问。不影响交付结果的实现细节，不要问。
- 一次只问最关键的一到两个问题。一口气列八个澄清点，需求方会挑最简单的那个答。
- 拿不准就说拿不准。不要用大词糊过去。

## 闸门

- `[闸门]` 需求定义卡五个字段全部非空。
- `[闸门]` `确认状态` 必须是 `confirmed`。`assumed` 直接驳回——**"我理解他要的应该就是……"不是确认**。
- `[闸门]` `验收标准` 必须可判定：含数字或可执行的检查方式。
- `[闸门]` 卡片里不得出现技术选型（出现说明越界到 02 了）。

## 驳回权

它是头，没有上游可打回。但**需求方可以驳回它**——退回去重来，且这是正常的，不是失败。

| 什么情况 | 打回给谁 | 附什么 |
|---|---|---|
| 需求方否认复述的需求定义 | 重新澄清 | 上一版卡片 + 被否认的具体条款 |

## 证据

需求定义卡本身（JSON），含确认时间戳与确认来源（哪条消息）。

## 反例

- ❌ "我先按我的理解开始，有问题再改。" → 越界。范围没定就开工，后面所有阶段都在赌。
- ❌ 把"活跃度用登录时间还是登录+业务操作"拿去问需求方之前，没先弄清楚技术上两条路的代价。→ 摆给需求方的是**取舍**，不是技术选项清单；代价查清楚是 02 的活。
- ❌ "一切正常，进展顺利。" → 零信息量，属于投影黑名单（`progress`）。

## 契约（机器可读）

上面每一条 `[闸门]` 在这里有一个谓词。改规则改这里与上文两处，`internal/pipeline` 会逐条判。
字段名就是交付物的字段名——没有第二个命名。

```json
{
  "id": "01",
  "name": "需求澄清",
  "produces": "需求定义卡",
  "entry": [],
  "exit": [
    { "field": "目标", "check": "nonempty" },
    { "field": "范围内", "check": "nonempty" },
    { "field": "范围外", "check": "nonempty" },
    { "field": "验收标准", "check": "nonempty" },
    { "field": "确认状态", "check": "equals", "value": "confirmed" }
  ]
}
```
