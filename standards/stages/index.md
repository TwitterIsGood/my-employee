# 阶段 spec 树

一个阶段 ≈ 一个 Agent ≈ 一个 spec 文件。规范分两层：

- **全局层**（对所有阶段生效）：[`delivery.md`](../delivery.md) 六要两不要、[`projection.md`](../projection.md) 投影、[`resilience.md`](../resilience.md) 上游韧性。
- **阶段层**（本目录）：每个阶段**额外**要守的东西。

```
需求澄清 → 技术方案设计 → 本地开发 → 自测 → 对抗式审查 → 部署验证 → 回归
  01          02           03        04        05          06       07
```

## 每个阶段的固定契约

七段都是同一个形状。**没有一个阶段靠"感觉做得差不多了"往下走。**

| 小节 | 回答什么 |
|---|---|
| 职责 | 这一段只干什么，不干什么 |
| **入口条件** | 上游须交付什么，我才开工 |
| **出口条件** | 我交付什么，下游才接受 |
| **专属规范** | 本阶段特有的规则（从全局准则派生） |
| `[闸门]` | 机器可判定的谓词，写不出谓词的规则视为**未落地** |
| **驳回权** | 什么情况打回、打回给谁、附什么 |
| 证据 | 怎么证明我真做了 |
| 反例 | 这一段最容易犯的错（取自真实事故） |
| **契约（机器可读）** | 上面 `[闸门]` 的谓词形态：一段 JSON |

**入口条件就是驳回权的依据。** 下游拿着上游的产物逐条对入口条件，对不上就打回——
不用凭感觉判断"这份交付够不够好"，那是没法复现的判断。

两处守着这张契约：

- [`internal/spec`](../../internal/spec) 守**形状**：任一阶段缺任一小节即测试失败。
- [`internal/pipeline`](../../internal/pipeline) 守**判定**：契约块当流水线定义读，读不出谓词的阶段文件直接报错。

## 契约块：规则只有一个事实源

每个阶段文件末尾的 ```json 块是上面 `[闸门]` 的谓词形态。**字段名就是交付物的字段名**，
没有第二套命名；改规则改散文与谓词两处，两者写在同一个文件里，不许各写一份。

```json
{
  "id": "02", "name": "技术方案设计", "produces": "方案卡",
  "entry":  [{ "from": "需求定义卡", "field": "范围外", "check": "nonempty" }],
  "exit":   [{ "field": "风险", "check": "min_items", "value": 1 }],
  "reject_to": "01"
}
```

还有个可选字段 `pause_on`：指向交付物里"我在等谁拍板"的字段（01 是 `待决策`）。

判定词只有七个：`present` / `nonempty` / `empty` / `is_true` / `equals` / `one_of` / `min_items`。
写不出谓词的条件不许上线——`internal/pipeline` 遇到不认识的判定词会**把这条判成不通过**，
不是跳过。

三条容易踩的：

- `when` 是**前置**：前置不成立则本条不适用（"通过"才要求列未覆盖范围）；
  但**前置字段缺失按不通过处理**——一条说不清前置的条件，等于一条会被静默跳过的闸门。
- `reject_upstream` 在入口条件来自不同上游时才需要：06 的变更卡缺字段打回 **03**，
  审查记录的问题打回 **05**。少了它，上游会收不到该补的东西。
- `reject_on` 管的是**本段自己的裁决**往回走，和入口条件不是一回事：入口没判定的是
  「上游没交够」，`reject_on` 判的是「交够了、但审出来有问题」。05 的
  `结论 = 驳回` 就走这条边。去向由交付物自己点名（`target_field`），
  所以同一段审查，反例指向 03、结构性缺陷指向 02、需求歧义指向 01，
  不用在契约里写死四份。理由同取交付物（`reasons_field`）——前台读到的是审查者
  写的那句「一个合法请求能让看板永久 500」，而不是一串字段名。

  ```json
  {
    "id": "05", "name": "对抗式审查", "produces": "审查记录",
    "entry":  [{ "from": "测试报告", "field": "退出码", "check": "present" }],
    "exit":   [{ "field": "结论", "check": "one_of", "value": ["通过", "驳回"] }],
    "reject_on": [{
      "when": [{ "field": "结论", "check": "equals", "value": "驳回" }],
      "target_field": "驳回至", "reasons_field": "驳回理由"
    }],
    "reject_to": "04"
  }
  ```

  **少了它，链路会原地打转**：05 合法交付（`结论=驳回`），06 的入口要 `结论=通过`，
  于是 06 把 05 退回来、05 不改结论（证据没变，改了就是伪造）、两边来回撞上返工上限，
  一个字节没往前挪。不是哪一段失职，是契约缺了一条边——详见
  [05-review.md](05-review.md)。

## 驳回怎么到前台

驳回不是后台的私事。`cmd/pipeline` 判不通过时产出一条 `blocker` 事件写进事件日志，
经 `cmd/gate` 投影成前台的「卡点」——需求方看到的是**卡在哪、因为哪几条**，
看不到后台来回打了几轮、谁跟谁有分歧（那是投影黑名单）。

## 六要两不要落在哪一段

顶层准则是全局的，但**每条准则在某个阶段被强制**。这张表是全局层与阶段层之间唯一的连接点：

| 准则 | 主执行阶段 | 说明 |
|---|---|---|
| 1 要测试 | **04 自测** | 回归套件全绿；数据路径变更须在测试环境跑通方案与回滚 |
| 2 要周知 | **06 部署验证** | 受影响方确认；范围本身在 01 定 |
| 3 要审核 | **06 部署验证** | 变更卡六字段 |
| 4 要灰度 | **06 部署验证** | 至少两级影响面递进 |
| 5 要观测 | **06 部署验证** | 每级灰度后已完成观测窗口 |
| 6 要可回滚 | **06 部署验证** | 代码 + 数据回滚，且在测试环境预演过 |
| 7 不要瞒报故障 | **06 部署验证** | 观测到异常时先上报再动 |
| 8 不要违规变更线上数据 | **03 本地开发** + 06 | 不得引入绕过鉴权/直连生产库的路径 |

于是 `delivery.md` 不必复制进每个阶段文件——阶段文件只说"这一段要守第 1 条"，读者回到唯一事实源。

## spec 怎么进到 Agent 里

跟投影同一个机制：**harness 侧注入，不靠 Agent 自觉**（理由见 [`projection.md`](../projection.md)）。

- 每个阶段的 Agent 通过自己的 `--settings` 带上对应的 spec 与全局准则的散文形态（`delivery.md` 形态 A）；
- `[闸门]` 的谓词形态（形态 B）进同一个 settings 的 hooks，判不了就 fail-closed。

**已落地**：`cmd/stage` 一次唤醒只跑一个阶段——

```
判入口（上游交齐没有） ──没交齐──▶ 打回上游，本阶段一次都不启动
        │交齐了
        ▼
   唤醒（spec 散文 + 上游交付物 + 需求方答复进 prompt）
        ▼
判出口（交付物逐条对出口条件）
        │
        ├──没过，但交付物里写着成形的一决策项 ──▶ 停在原地等人（不算失败）
        │                                       取舍经投影出门 → 答复经 --brief 回来 → 叫醒同一段
        ├──没过 ──▶ 带原因重跑，预算用尽则升级给人工指导者
        ▼过了
   判裁决（reject_on）
        │
        ├──判出"上游有问题" ──▶ 退回交付物点名的那一段（05 判驳回 → 03）
        ▼没判出
     下一阶段
```

**出口过了不等于这一趟就该往下走。** 交付物里可能写着「上游有问题」——05 的
`结论 = 驳回` 就是。往回走要在出口之后、交给下游之前拦，出了出口就当成了，
下游会拿一条它自己的入口条件把这份合法的交付退回来，两边对着卡死。

`cmd/chain` 把上面这一段接起来跑到底。它比 `cmd/stage` 多知道两件事，也只有它在算这两笔账：

- **下一段是哪一段。** 最后一段过了就收尾，并记一条「全部阶段已完成」——否则前台那行
  「阶段」会停在「07 回归」上，那是上一段的动作，不是这条需求的状态。
- **被打回时退到哪一段。** 退到**最靠前**的回退点：打回 03 与 05 两段时从 03 重走，
  04、05 会在路上重新被判一次；从 05 走会让 03 的补交没人验收。

**打回的条要跟着往回走。** 06 说变更卡缺六字段而把 03 退回去，那段话必须进 03 下一次的
prompt。少了它，03 会拿着和上次一样的输入再交一遍同样的东西——驳回权就成了一道手续。
这笔账（`back`）跟链路的断点写在一起：链路断了再续，那一段接到的还是原来那几条。
这一段交过之后就销账，留着它，下一趟续跑会拿两轮以前的原因去叫醒它。

**返工有上限，撞了就升级。** 单段的 `budget` 管不住「03 改完 05 又打回」这种来回，
只有整条链看得见这个循环，所以这笔账记在链上（`--max-rework`）。撞了南墙是**链路的出口**，
不是又一次重试——它和「停在原地等人」是两种结局，必须分开。

`--max-rework` 要按「结构性的一轮 + N 轮真问题」留余量：真实七段树**每一趟都至少一轮**
结构性的返工——06 的入口要变更卡的六字段，其中 `测试报告` 指向 04 的产物，
03 在自己那一步交不出来。那一轮不是出错，是 06 在按准则 3 查卡、查出来退回 03 补齐
（见 [03-develop.md](03-develop.md) 与 [06-deploy.md](06-deploy.md) 的契约一节）。

**卡点会被撤下来。** 一段被打回、后来又补交通过，那条卡点就从投影里消失——
前台那份文档是**当前状态**，不是流水账。不撤的结果是真实见过的：链路已经走完，
投影里「阶段：全部阶段已完成」和「本地开发 的交付被打回」并排挂着，
读的人不知道该不该管它。规则见 [`projection.md`](../projection.md)。

**断点落在文件里。** 每次推进都写 `chain.json`（走到哪、已过哪几段、返工几次）。
这条链路会断——停在等人、撞上南墙、或者某段预算用尽——断了就得能续，
所以位置不靠「目录里有哪些交付物」去猜：那种推断会被上一次驳回留下的旧产物骗过去。

**停在原地等人**和**撞南墙**是两种结局，必须分开：重跑多少次都问不出需求方本人的答案。
把它算成失败，会让人去修一个本来就该等人回答的东西。

`pause_on` 指的就是交付物里那个"我在等谁"的字段（01 是 `待决策`）。
**说不清的暂停不算暂停**——字段缺失、选项少于两个、选项不带代价，一律掉回重跑。
否则"我在等人"就是一条绕开出口条件的捷径。

阶段之间**不靠 Agent 互相喊话**：上游的产物落成文件，下游拿文件逐条对入口条件。
这样状态不会被两个 Agent 的对话悄悄改掉——对得上就是一份可复现的判定，
对不上就是一条写明了原因的驳回。

两处判定都在 Agent **之外**发生，Agent 看不到判定过程，只看到"没过，因为这几条"。
它没法跟判定讲价，只能把交付物改到过为止。逐次重跑属过程（投影黑名单的 `retry`），
不出口；只有终局——过了，或撞了南墙升级——才可能被前台看见。
