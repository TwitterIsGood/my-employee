# 阶段 spec 树

一个阶段 ≈ 一个 Agent ≈ 一个 spec 文件。规范分两层：

- **全局层**（对所有阶段生效）：[`delivery.md`](../delivery.md) 六要两不要、[`projection.md`](../projection.md) 投影、[`resilience.md`](../resilience.md) 上游韧性。
- **阶段层**（本目录）：每个阶段**额外**要守的东西。

```
需求澄清 → 技术方案设计 → 本地开发 → 自测 → 对抗式审查 → 部署验证 → 回归
  01          02           03        04        05          06       07
```

## 每个阶段的固定契约

七段都是同一个形状。**没有一个阶段靠"感觉做得差不多了"往下走。**

| 小节 | 回答什么 |
|---|---|
| 职责 | 这一段只干什么，不干什么 |
| **入口条件** | 上游须交付什么，我才开工 |
| **出口条件** | 我交付什么，下游才接受 |
| **专属规范** | 本阶段特有的规则（从全局准则派生） |
| `[闸门]` | 机器可判定的谓词，写不出谓词的规则视为**未落地** |
| **驳回权** | 什么情况打回、打回给谁、附什么 |
| 证据 | 怎么证明我真做了 |
| 反例 | 这一段最容易犯的错（取自真实事故） |

**入口条件就是驳回权的依据。** 下游拿着上游的产物逐条对入口条件，对不上就打回——
不用凭感觉判断"这份交付够不够好"，那是没法复现的判断。

契约本身由 [`internal/spec`](../../internal/spec) 的测试守着：任一阶段缺任一小节即测试失败。

## 六要两不要落在哪一段

顶层准则是全局的，但**每条准则在某个阶段被强制**。这张表是全局层与阶段层之间唯一的连接点：

| 准则 | 主执行阶段 | 说明 |
|---|---|---|
| 1 要测试 | **04 自测** | 回归套件全绿；数据路径变更须在测试环境跑通方案与回滚 |
| 2 要周知 | **06 部署验证** | 受影响方确认；范围本身在 01 定 |
| 3 要审核 | **06 部署验证** | 变更卡六字段 |
| 4 要灰度 | **06 部署验证** | 至少两级影响面递进 |
| 5 要观测 | **06 部署验证** | 每级灰度后已完成观测窗口 |
| 6 要可回滚 | **06 部署验证** | 代码 + 数据回滚，且在测试环境预演过 |
| 7 不要瞒报故障 | **06 部署验证** | 观测到异常时先上报再动 |
| 8 不要违规变更线上数据 | **03 本地开发** + 06 | 不得引入绕过鉴权/直连生产库的路径 |

于是 `delivery.md` 不必复制进每个阶段文件——阶段文件只说"这一段要守第 1 条"，读者回到唯一事实源。

## spec 怎么进到 Agent 里

跟投影同一个机制：**harness 侧注入，不靠 Agent 自觉**（理由见 [`projection.md`](../projection.md)）。

- 每个阶段的 Agent 通过自己的 `--settings` 带上对应的 spec 与全局准则的散文形态（`delivery.md` 形态 A）；
- `[闸门]` 的谓词形态（形态 B）进同一个 settings 的 hooks，判不了就 fail-closed；
- 一次唤醒只跑一个阶段，跑完把**已确认的事实**写进事件日志，由 `cmd/gate` 投影给前台——阶段之间不靠 Agent 互相喊话传递状态。
